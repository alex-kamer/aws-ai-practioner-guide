2.1 Explain the basic concepts of generative AI

Generative AI creates new content (text, images, audio, code, video) by learning the statistical patterns of very large training sets and then sampling from those patterns. Full definitions are in the glossary; this section explains how the pieces fit together.

Tokens and tokenization

A model never sees raw text. A tokenizer first splits text into tokens: whole words, word fragments, punctuation, or bytes. Each token maps to an integer ID, and the model works on those IDs. Common words are often one token, while rare words, names, and code are split into several. As a rough English rule of thumb, one token is about three-quarters of a word, but each model family has its own tokenizer, so counts differ between models.

Tokens matter for three practical reasons. First, cost: on-demand pricing is per input token and per output token. Second, limits: the context window and maximum output length are measured in tokens. Third, latency: the model produces output one token at a time, so longer answers take longer.

Worked example: a 2,000-token document plus a 100-token instruction is 2,100 input tokens. If the model writes a 300-token summary, you are billed for 2,100 input tokens and 300 output tokens. Output tokens are usually priced higher than input tokens.

Embeddings and vector similarity

An embedding is a list of numbers (a vector, often hundreds to thousands of dimensions) produced by an embedding model so that text with similar meaning lands close together in vector space. Think of a map where "refund policy" and "return an item" sit in the same neighborhood even though they share no words, while "weather forecast" is far away.

"Close" is measured with a distance or similarity function such as cosine similarity or Euclidean distance. To search, you embed the query, then ask a vector database for the nearest stored vectors. This is semantic search, and it is the retrieval step in Retrieval Augmented Generation (RAG). Embeddings can also be made for images, so text can be matched to pictures in a multimodal embedding space.

Chunking

Documents are too long and too varied to embed as one vector. Chunking splits them into passages (for example a few hundred tokens each, often with some overlap) before embedding. Chunks that are too large blur several topics into one vector and waste context window space. Chunks that are too small lose the surrounding meaning. Overlap helps a sentence that straddles a boundary stay retrievable. In Amazon Bedrock Knowledge Bases, chunking is part of the managed ingestion process and you can choose a chunking strategy.

Transformers and attention, intuitively

Older sequence models read text word by word and struggled with long-range links. The transformer architecture uses self-attention: for every token, the model computes how much it should "look at" every other token when building its meaning. In "The trophy did not fit in the suitcase because it was too big", attention lets the model weigh that "it" refers to the trophy. Because all tokens can be processed in parallel, transformers train efficiently on large hardware clusters, which is what made today's scale possible.

An LLM is a transformer trained on huge text corpora to predict the next token. Repeating that prediction one token at a time produces whole answers. Summarizing, translating, and answering questions all emerge from this single objective plus instruction tuning.

Diffusion models

A diffusion model is trained by taking real images, adding noise step by step until only static remains, and learning to reverse each step. To generate, it starts from pure noise and removes noise repeatedly, guided by a text prompt, until an image appears. Analogy: a sculptor who starts with a rough block and gradually reveals the shape. Diffusion is the main approach behind modern image generation, and similar ideas are used for video. Amazon Titan Image Generator and Stability AI image models on Bedrock are image-generation examples.

Multimodal models

A multimodal model accepts or produces more than one data type, such as text plus images. Examples: describing a chart from a screenshot, answering questions about a photo, or turning a text description into an image. Check the model card in Bedrock for which input and output modalities each model supports, since a text-only LLM cannot read an image.

Prompts and the context window

The prompt is everything you send: instructions, examples, retrieved documents, and the user question. The context window is the maximum number of tokens (input plus output) the model can consider at once. Anything beyond it is not seen. A model has no memory between calls beyond what you include in the prompt, so a chatbot "remembers" by resending earlier turns. Prompt engineering shapes the prompt to get better output without changing the model.

Inference parameters: temperature, top-p, top-k

At each step the model assigns a probability to every possible next token, then one is sampled. These settings control the sampling:

ParameterWhat it doesTypical use
TemperatureReshapes the probabilities. Low values favor the most likely tokens; high values flatten the distribution.Low for factual extraction or code; higher for brainstorming and creative writing
Top-pSamples only from the smallest set of tokens whose probabilities add up to p (for example 0.9).Lower p for focused output
Top-kSamples only from the k most likely tokens.Lower k for more predictable output

These parameters change randomness, not knowledge. A low temperature makes output more repeatable, but it does not make a wrong fact right.

Foundation model lifecycle

Data selection -> Model selection -> Pre-training -> Fine-tuning -> Evaluation -> Deployment -> Feedback
  1. Data selection: choose and clean the data, considering quality, diversity, licensing, and privacy.
  2. Model selection: pick an architecture or an existing FM that fits modality, size, cost, and latency needs.
  3. Pre-training: self-supervised learning on massive unlabeled data. Very expensive, so most organizations skip it and start from an existing FM.
  4. Fine-tuning: further training on a smaller, labeled, task- or domain-specific dataset to specialize the model.
  5. Evaluation: measure quality with benchmarks, automatic metrics, and human review against your goals.
  6. Deployment: serve the model, for example through Bedrock or a SageMaker endpoint, with monitoring and guardrails.
  7. Feedback: collect user and monitoring signals to improve prompts, data, and future model versions, which loops back to earlier stages.

Generative AI use cases

Use caseWhat it looks like

Exam tip: Match the keyword to the concept: "denoising" means diffusion, "numeric representation of meaning" means embedding, "attention" means transformer, "more than one data type" means multimodal, "pay per input/output token" means on-demand.

Common trap: Pre-training and fine-tuning are not the same. Pre-training builds general ability from unlabeled data; fine-tuning specializes with a smaller labeled dataset. Also, a larger context window does not mean the model remembers earlier conversations.

Key takeaways

  • Text becomes tokens; tokens drive cost, limits, and latency.
  • Embeddings place meaning in vector space; chunking prepares documents for embedding.
  • Transformers use attention; LLMs predict the next token; diffusion models denoise.
  • Temperature, top-p, and top-k control randomness only.
  • The lifecycle runs from data selection to feedback, and loops.

2.2 Capabilities and limitations for business problems

Advantages

  • Adaptability: one foundation model can summarize, classify, translate, and answer questions, steered by prompts, retrieval, or fine-tuning, instead of one custom model per task.
  • Responsiveness: answers arrive in seconds, so support, drafting, and analysis workflows speed up and can run around the clock.
  • Simplicity: a natural-language interface lowers the skill barrier. A prototype can be a prompt and an API call, not a months-long training project.

Limitations and risks

  • Hallucination: the model optimizes for plausible next tokens, not truth, so it can state invented facts, citations, or API names fluently. Mitigate with RAG, grounding checks, lower temperature, and human review.
  • Interpretability: billions of parameters make it hard to explain why a specific output was produced, which is a problem in regulated decisions.
  • Inaccuracy: outputs can be wrong, outdated (training data has a cutoff), or biased.
  • Nondeterminism: sampling means the same prompt can give different answers. That is fine for brainstorming but awkward for testing and audit.
  • Cost: large models cost money per token and per hour of hosted capacity; long prompts and long answers multiply it.
  • Data privacy and security: sending sensitive data to a model, or leaking it in outputs, creates exposure. Prompt injection is a related risk.
  • Intellectual property: training data and generated output can raise copyright and licensing questions.

Choosing a model for a business problem

Start from the problem, not the model. Consider the modality needed (text, image, both), required quality, latency, cost per request, context window size, customization options (prompting, RAG, fine-tuning), language support, and compliance or data-residency constraints. Bigger is not automatically better: a smaller, cheaper model often meets a narrow task, and a large one is justified only when the quality gain pays for itself. Evaluate candidates on your own prompts, for example with Bedrock model evaluation, before committing.

Measuring business value

MetricWhat it asksExample
EfficiencyIs work faster or cheaper per unit?Support handle time drops from 10 to 6 minutes
Conversion rateDo more visitors buy or sign up?Generated product copy lifts checkout rate
Average revenue per user (ARPU)Does each user generate more revenue?Personalized recommendations raise basket size
Customer lifetime valueDo customers stay and spend longer?Better service improves retention
Cross-domain performanceDoes the model perform well across varied tasks and domains?One model serves legal, HR, and support teams
AccuracyAre outputs correct for the task?Share of summaries judged faithful

Pair a business metric with a technical one. A model with excellent benchmark scores that does not move conversion or efficiency has not delivered value.

Exam tip: Scenario questions usually map a stated goal to a metric: "sell more per visit" is ARPU or conversion, "long-term retention" is customer lifetime value, "save staff time" is efficiency.

Common trap: Low temperature reduces variation but does not remove hallucination. Only grounding (RAG), verification, and human oversight address wrong facts.

Key takeaways

  • Strengths: adaptability, responsiveness, simplicity.
  • Weaknesses: hallucination, interpretability, inaccuracy, nondeterminism, cost, privacy, IP.
  • Pick models by fit to the task, constraints, and measured business outcomes.

2.3 AWS infrastructure and technologies for GenAI apps

AWS offers GenAI at several levels of abstraction. A useful mental model: ready-made applications (Amazon Q) at the top, managed model access and building blocks (Bedrock) in the middle, and self-managed model hosting (SageMaker) at the bottom. The higher you go, the less you build and the less control you have.

ServiceRoleChoose it when
Amazon BedrockServerless API access to foundation models from several providers, plus Knowledge Bases, Agents, Guardrails, and model evaluationYou are building your own GenAI application and want managed models
SageMaker JumpStartHub of pre-trained models and solution templates deployed to endpoints you controlYou need more control over hosting, instance types, or models not offered in Bedrock
PartyRockNo-code playground for building small GenAI apps, backed by BedrockYou want to experiment or learn without writing code
Amazon QReady-made GenAI assistants (Business, Developer)You want an assistant, not a platform to build one
Amazon TitanAWS's own FM family, available in BedrockYou want an AWS-built text, embeddings, or image model

Amazon Bedrock in depth

  • Model catalog: one API over models from multiple providers (for example Amazon, Anthropic, Meta, Mistral AI, Cohere, AI21 Labs, Stability AI). You can swap models by changing the model ID, which makes side-by-side comparison easy. Your prompts and data are not used to train the base models offered through Bedrock.
  • Knowledge Bases: managed RAG. You point it at a data source (such as S3); it chunks, embeds, and stores the content in a vector store, then retrieves relevant passages and supplies them to the model at query time. This grounds answers in your current data without retraining.
  • Agents: let a model plan and carry out multistep tasks, such as looking up an order and then issuing a refund, by calling your APIs (through action groups) and optionally consulting a knowledge base.
  • Guardrails: configurable safeguards applied to inputs and outputs, such as content filters, denied topics, word filters, and sensitive-information (PII) filters, and a contextual grounding check against hallucination. They work across models.
  • Model evaluation: compare models or settings using automatic metrics, or human reviewers, on your own datasets.
  • Customization: fine-tuning and continued pre-training for supported models; the result is a custom model.

Other services

  • SageMaker JumpStart: start from a pre-trained or open model, deploy it to a SageMaker endpoint, optionally fine-tune. You manage endpoint capacity, which gives control but more operational work than Bedrock.
  • PartyRock: build shareable apps by describing them in a browser. It is for experimentation and learning, not production workloads.
  • Amazon Q Business: an assistant for employees that connects to enterprise data sources and answers questions from them, respecting existing user access permissions.
  • Amazon Q Developer: an assistant for software work: code suggestions and generation, explaining and debugging code, and help with AWS questions, available in IDEs and the console.
  • Amazon Titan: includes text generation models, text and multimodal embedding models, and an image generator, all accessed through Bedrock.

Why build on AWS

  • Accessibility and lower barrier to entry: API access and no-code tools mean teams without ML specialists can start.
  • Speed to market: no GPU procurement or model hosting; prototype to production quickly.
  • Security: encryption, IAM access control, private connectivity options, and logging with the usual AWS tooling.
  • Compliance: AWS maintains many compliance programs; you still own your configuration and use of them under the shared responsibility model.
  • Responsible AI and safety: built-in controls such as Guardrails.
  • Cost-effectiveness: pay-as-you-go, with options to commit for steady workloads.

Cost model

OptionHow you payBest for
On-demandPer input and output token (images are priced per image); no commitmentVariable or unpredictable traffic, prototypes
BatchSubmit many prompts as a job and get results later, typically at a lower price than on-demandLarge offline jobs that are not latency sensitive
Provisioned throughputReserve model units for an hourly rate, with optional commitment termsSteady high-volume workloads needing consistent performance; the standard way to serve custom models

Worked example: a nightly job that classifies 500,000 support tickets can wait until morning, so batch inference is a good fit. A customer chatbot with a steady, heavy load and strict latency expectations may justify provisioned throughput. A prototype used by ten people should be on-demand.

Other cost and design factors: Region (model availability and price vary, and data residency rules may limit where you can run), redundancy and availability (design across Availability Zones or Regions as needed), response time, and model size. Cost also scales with prompt length, so trimming prompts and retrieving only relevant chunks saves money.

Exam tip: "No infrastructure to manage, many models, one API" is Bedrock. "Ground answers in my documents" is Knowledge Bases. "Block harmful or off-topic content" is Guardrails. "Multistep tasks calling APIs" is Agents. "Employees ask questions about internal data" is Q Business. "Help developers write code" is Q Developer.

Common trap: Do not choose provisioned throughput just because traffic is high-sounding; it is the answer for sustained, predictable load or custom models. Also, PartyRock is not a production platform, and JumpStart is not serverless like Bedrock.

Key takeaways

  • Bedrock is the managed, multi-model hub; JumpStart gives more control; Q provides ready-made assistants; PartyRock is for no-code experiments.
  • Knowledge Bases ground, Agents act, Guardrails protect, evaluation compares.
  • Pricing: on-demand per token, batch for offline jobs, provisioned throughput for steady load and custom models.
  • AWS value: speed, security, compliance, responsible AI tooling, and flexible cost.

    Hallucinations, interpretability issues, inaccuracy, nondeterminism.

    The same prompt can produce different outputs.

  7. Which service gives API access to many FMs without managing servers?

    Amazon Bedrock.

  8. How do Bedrock and SageMaker JumpStart differ?

    Bedrock is serverless API access to FMs; JumpStart deploys pre-trained models onto endpoints you manage.

  9. When would you choose provisioned throughput over on-demand?

    Steady high-volume workloads needing guaranteed throughput, or when using a custom model.

  10. Which AWS tool is a no-code place to experiment with GenAI apps?

    PartyRock; it is a Bedrock-backed playground meant for experimenting, not production.

  11. A team wants factual extraction that returns nearly the same answer on every run. Which inference setting should they adjust?

    Lower the temperature (and optionally top-p/top-k); this makes the model favor the most likely tokens, reducing randomness.

    Bedrock Knowledge Bases (RAG); it retrieves relevant chunks at query time and supplies them to the model.

  13. An online retailer measures whether generated recommendations make each shopper spend more. Which metric fits?

    Average revenue per user (ARPU); it tracks revenue generated per customer.

  14. A bank needs to stop its assistant from discussing investment advice and from echoing account numbers. Which feature helps?

    Bedrock Guardrails; denied topics and sensitive-information filters apply to inputs and outputs.

  15. A firm must classify 500,000 documents overnight, with no need for instant results. Which Bedrock mode is the most cost-aware choice?

    Batch inference; it processes large offline jobs, typically at a lower price than on-demand.
